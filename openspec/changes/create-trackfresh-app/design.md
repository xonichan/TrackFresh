# Design

## Context

См. proposal.md — Why. Приложение ещё не написано. Серверная часть уже существует: схема PostgreSQL и правила доступа (`data-model`), API (`data-api`, каталог `api/`, документация `docs/api.md`). Аутентификация — Firebase Authentication. Спеки `product-management`, `expiration-notifications`, `user-data-sync`, `data-api` описывают требуемое поведение; это изменение их реализует.

## Goals / Non-Goals

**Goals:**
- Android-приложение, читающее и меняющее свои данные через HTTP API.
- OCR упаковки с предзаполнением формы.
- Локальные напоминания о сроках годности.
- Общая логика экранов без дублирования кода запросов.

**Non-Goals:**
- Работа без сети (офлайн).
- Серверный планировщик рассылки push — отдельное изменение.
- iOS, семейный доступ, штрих-коды.
- Изменения API и схемы БД.

## Decisions

### 1. Expo prebuild + dev-client, не Expo Go
**Выбор**: с первого шага `expo prebuild` и `expo-dev-client`.
**Rationale**: Expo Go не содержит нативных модулей ML Kit и Firebase Auth; с ними приложение просто не соберётся в Expo Go. Прежний план начинался с `expo start`, что противоречило задачам установки нативных зависимостей.
**Альтернатива**: bare React Native — тот же prebuild, но ручная настройка навигации и обновлений.

### 2. Данные — только через HTTP API
**Выбор**: единственный путь к данным — `api/` (спека `data-api`); Firestore не используется.
**Rationale**: хранилище уже переведено на PostgreSQL, правила доступа и изоляция реализованы на сервере.
**Следствие**: без сети приложение не работает — это осознанный отказ, а не недосмотр.

### 3. Аутентификация: Firebase Auth + ID-токен в заголовке
**Выбор**: вход email/пароль и Google Sign-In; каждый запрос несёт `Authorization: Bearer <ID token>`.
**Rationale**: сервер проверяет токен и сам находит профиль по `firebase_uid`; приложение не знает `users.id`.
**Следствие**: клиент не обязан знать внутренние идентификаторы — только токен.

### 4. ML Kit для OCR
**Выбор**: `@react-native-ml-kit/text-recognition`.
**Rationale**: нативное распознавание без сети, лучше по качеству, чем Tesseract.js.
**Альтернатива**: Tesseract.js — хуже качество, требует загрузки WASM.

### 5. Навигация: React Navigation (Bottom Tabs + Stack)
**Выбор**: вкладки «Список», «Добавить», «Настройки» + стек для деталей и правки.
**Rationale**: стандартный паттерн; экран входа показывается вне вкладок, когда пользователь не аутентифицирован.

### 6. Напоминания: только локальные
**Выбор**: `expo-notifications`, расписание на устройстве.
**Rationale**: серверный триггер требует Cloud Functions и плана Blaze. Локальные напоминания не зависят от Firebase и укладываются в текущий объём.
**Открыто**: доставка push из серверного планировщика — отдельным изменением.

### 7. Стейт: Context API + useReducer, слой запросов отдельно
**Выбор**: Context для состояния экранов; обращения к API — в одном модуле-клиенте.
**Rationale**: масштаб мал (одна сущность), но логика запросов и разбора ошибок не должна расползаться по экранам.

### 8. Цветовой порог берётся из настроек
**Выбор**: «истекает скоро» считается по `warnDays` из `GET /settings`, а не по жёстким 3 дням.
**Rationale**: спека `product-management` жёстко называет 3 дня, но период предупреждения настраивается в `expiration-notifications`; две константы для одного смысла разошлись бы.

## Risks / Trade-offs

- **[Приватный адрес `192.168.3.69`]** → вне домашней сети API недоступен, приложение бесполезно. Митигация: вынести доступ наружу (VPN или публикация) отдельным решением до реального использования.
- **[Нет офлайна]** → без сети нельзя ни посмотреть список, ни добавить продукт. Митигация: явный экран ошибки с повтором запроса; офлайн — отдельным изменением.
- **[OCR-качество]** → нестандартные форматы дат не распознаются. Митигация: всегда показывать предзаполненную форму для ручной правки.
- **[Dev-client вместо Expo Go]** → сборка требует Android SDK и локальной сборки, «поделиться ссылкой» не выйдет. Митигация: принять как цену за нативные модули.
- **[Сервер вне объёма]** → напоминания по расписанию на сервере не делаются, спека `expiration-notifications` останется частично нереализованной. Митигация: зафиксировано в proposal и в вопросах ниже.

## Open Questions

- Как приложение попадёт в сеть `192.168.3.69` (VPN, перенаправление порта, туннель) — решается до эксплуатации.
- Нужен ли TLS для API до выхода за пределы домашней сети.
- Как запускать сервер (systemd, Docker, pm2) — при развёртывании.
