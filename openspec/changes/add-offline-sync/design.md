# Design

## Context

См. proposal.md — Why. Клиент (`create-trackfresh-app`) сейчас читает и пишет только через API: без сети экран показывает ошибку с повтором. API (`data-api`) возвращает продукты без `updated_at` и не принимает идентификатор клиента. Схема БД менять не нужно: `products.updated_at` уже есть.

## Goals / Non-Goals

**Goals:**
- Данные доступны без сети, изменения не теряются.
- Отправка отложенных изменений без участия пользователя.
- Предсказуемое разрешение расхождений без диалогов.

**Non-Goals:**
- Выбор пользователем версии при конфликте.
- Фоновая синхронизация через системный планировщик (работает, пока приложение открыто).
- Совместная работа нескольких пользователей над одним списком.

## Decisions

### 1. Локальное хранилище — AsyncStorage
**Выбор**: `@react-native-async-storage/async-storage`, три ключа: продукты, настройки, очередь.
**Rationale**: десятки записей, запросов с фильтрацией на клиенте нет — вся выборка делается в памяти. SQLite дал бы схему и миграции без пользы.
**Альтернатива**: `expo-sqlite` — нужен при сотнях записей и частичной загрузке.

### 2. Идентификатор продукта создаёт клиент
**Выбор**: `uuid` генерируется на клиенте при добавлении, уходит в `POST /products` как `id`.
**Rationale**: единственный надёжный способ не создать дубликат, если ответ на создание потерялся. Сервер уже умеет хранить заданный `id` — тип `uuid` с `DEFAULT`, а не `GENERATED ALWAYS`.
**Следствие**: `POST` становится идемпотентным по `id` (см. дельту `data-api`).

### 3. Очередь операций с уплотнением
**Выбор**: запись `{op: 'create'|'update'|'delete', productId, payload, at}`; перед отправкой одинаковые операции по одному продукту схлопываются в последнюю.
**Rationale**: пользователь может править продукт несколько раз подряд; отправлять промежуточные состояния незачем.
**Правило**: `create` + `update` → `create` с итоговыми полями; `create` + `delete` → обе удаляются (продукт не покидал устройство); `delete` после `update` → только `delete`.

### 4. «Побеждает последний» по `updated_at`
**Выбор**: перед отправкой `update` клиент сравнивает `updated_at` серверной копии (из последней загрузки) с `at` локальной правки; если сервер новее — правка отбрасывается.
**Rationale**: одно сравнение, без дополнительных запросов.
**Ограничение**: опора на часы устройства. Если часы врут, выбор будет неверным — риск зафиксирован.

### 5. Повтор отправки по таймеру, без отдельной библиотеки сети
**Выбор**: пока очередь не пуста, повтор каждые 30 секунд, плюс попытка при старте приложения и при обновлении списка.
**Rationale**: `@react-native-community/netinfo` — ещё один нативный модуль и ещё одна сборка; для одного пользователя таймера достаточно.
**Альтернатива**: NetInfo — точнее ловит момент появления сети.

### 6. Ответы сервера, означающие «уже сделано»
**Выбор**: `404` при `update` — продукт удалён на другом устройстве, правку отбрасываем; `404` при `delete` и `409` при `create` с занятым идентификатором — считаем операцию выполненной (для 409 продукт принадлежит другому профилю, значит наш уже не существует).
**Rationale**: иначе очередь застрянет навсегда на операции, которую сервер уже не примет.

### 7. Порядок записи
**Выбор**: сначала пишем в локальное хранилище, потом обновляем экран.
**Rationale**: падение между шагами не должно оставлять экран с данными, которых нет на диске.

## Risks / Trade-offs

- **[Часы устройства]** → при неверном времени «побеждает последний» выберет не ту версию. Митигация: принять; при явном расхождении показывать, что данные пришли с сервера.
- **[Молчаливая потеря правки]** → решение принято осознанно. Митигация: индикация «данные обновлены с сервера» после выравнивания.
- **[Рост очереди]** → при долгой недоступности API очередь копится. Митигация: уплотнение по продукту ограничивает размер числом продуктов.
- **[AsyncStorage без транзакций]** → две записи подряд не атомарны. Митигация: писать один ключ за операцию, порядок «диск, потом экран».
- **[Фоновая работа]** → синхронизация идёт только при открытом приложении. Митигация: принято, вынесено в Non-Goals.

## Migration Plan

1. Расширить API (`updated_at` в ответах, приём `id` при создании) и проверить тестами.
2. Добавить локальное хранилище и очередь; покрыть уплотнение и выбор версии тестами.
3. Переключить чтение данных на локальный кэш, запись — на очередь.
4. Проверить сценарии: работа без сети, появление сети, конфликт в обе стороны.
5. Откат: убрать чтение из кэша — приложение возвращается к прежнему поведению, локальные данные остаются на устройстве.

## Open Questions

- Нужен ли системный планировщик для синхронизации в фоне — отдельным изменением.
- Что показывать, если очередь не уходит несколько дней подряд.
