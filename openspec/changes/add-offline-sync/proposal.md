# Proposal

## Why

Приложение работает только при доступном API: без сети список пустой, добавить продукт нельзя. Для домашнего сценария это заметно — в магазине и на кухне связь бывает плохой, а продукт нужно записать сразу. Кроме того, единственный барьер — проверка токена на сервере; потерянная правка не должна приводить к потере данных.

## What Changes

- Появляется локальное хранилище на устройстве: продукты и настройки доступны без сети.
- Добавление, изменение и удаление продуктов работают без сети: изменения сразу видны в списке и попадают в очередь отправки.
- Очередь уходит на сервер, когда связь появляется; при успехе локальные данные выравниваются с серверными.
- Конфликты разрешаются по времени изменения: побеждает более позднее.
- **API**: ответы с продуктом начинают содержать `updated_at` — без него не с чем сравнивать время изменения.
- **API**: создание продукта становится идемпотентным — клиент присылает свой идентификатор, повторная отправка не создаёт дубликат.

## Capabilities

### New Capabilities

- `offline-sync`: локальный кэш данных, очередь изменений, отправка при появлении связи и разрешение конфликтов по времени изменения.

### Modified Capabilities

- `data-api`: продукт в ответах несёт `updated_at`; создание принимает идентификатор клиента и не создаёт дубликат при повторе.

## Impact

- Клиент: локальное хранилище (`@react-native-async-storage/async-storage`), модуль очереди, синхронизатор, индикация «офлайн» и числа неотправленных изменений.
- Сервер (`api/`): `PRODUCT_COLUMNS` с `updated_at`, приём необязательного `id` при создании, ответ на повтор.
- Схема БД не меняется: `products.updated_at` уже существует.
- Риск: при «побеждает последний» чужая правка теряется молча — это принятое решение, но пользователь должен видеть, что данные обновились с сервера.
- Вне объёма: разрешение конфликтов с выбором пользователя, фоновая синхронизация через системный планировщик, push-рассылка.
