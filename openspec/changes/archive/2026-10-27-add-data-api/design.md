# Design

## Context

См. proposal.md — Why. Схема PostgreSQL уже создана и защищена RLS (миграции `0001`, `0002`; спеки `data-model`, `user-data-sync`). Аутентификация остаётся на Firebase Authentication: профиль содержит `firebase_uid`. Кода приложения и сервера в репозитории ещё нет.

## Goals / Non-Goals

**Goals:**
- Дать приложению единственный документированный способ читать и менять свои данные.
- Установить доверенную границу: клиент не имеет доступа к базе напрямую.
- Обеспечить изоляцию данных на уровне запроса.

**Non-Goals:**
- Клиентский код и его интеграция.
- Офлайн-режим, push-уведомления, внешний доступ и TLS.
- Изменения схемы БД.

## Decisions

### 1. Node.js + Express + TypeScript, REST поверх JSON
**Выбор**: обычные REST-эндпоинты `/products`, `/settings`, JSON-тела.
**Rationale**: один рантайм с React Native, общий язык, минимум бойлерплейта.
**Альтернативы**: NestJS — строже, но избыточен; GraphQL — гибче, но лишняя сложность для CRUD.

### 2. Проверка Firebase ID-токена через `firebase-admin`
**Выбор**: middleware проверяет токен и извлекает `uid`.
**Rationale**: доверяем подписи Firebase; собственных паролей сервер не хранит.
**Альтернатива**: клиент передаёт uid — недопустимо, подделывается.

### 3. Идентичность в RLS — через транзакцию и `SET LOCAL`
**Выбор**: каждый запрос выполняется в транзакции, где сначала `SET LOCAL app.user_id = <users.id>`.
**Rationale**: `SET` на уровне сессии в пуле соединений «протекает» между запросами и может показать чужие строки. `SET LOCAL` действует только до конца транзакции.
**Альтернатива**: отдельное соединение на запрос — дорого; глобальный `SET` — опасно.

### 4. Резолв `firebase_uid → users.id` и создание профиля
**Выбор**: перед установкой `app.user_id` выполняется поиск профиля по `firebase_uid`; при отсутствии — `INSERT` профиля.
**Rationale**: `users.id` — суррогатный uuid, клиент его не знает; `firebase_uid` — единственная привязка к учётной записи.
**Следствие**: один дополнительный запрос на обращение; результат кэшируется в процессе.

### 5. Даты — текстом из базы
**Выбор**: `to_char(expiry_date, 'YYYY-MM-DD')` в выборках и приём `YYYY-MM-DD` на входе.
**Rationale**: драйвер `pg` возвращает `date` как JS `Date` в локальной зоне и сдвигает календарную дату (зафиксировано в `docs/data-model.md`).

### 6. Модель ошибок
**Выбор**: 401 — токен; 422 — нарушение ограничений (`23514`, `23502`); 404 — чужая или отсутствующая строка; 409 — конфликт уникальности (`23505`).
**Rationale**: коды ограничений PostgreSQL дают однозначный маппинг без разбора текста.

### 7. Проверка токена — за интерфейсом
**Выбор**: зависимость «верификатор токена» внедряется, в тестах подменяется.
**Rationale**: иначе автотесты требовали бы реальных Firebase-токенов.

## Risks / Trade-offs

- **[`SET LOCAL` вне транзакции]** → политика не применится и запрос увидит 0 строк или ошибочно чужие. Митигация: единая обёртка запроса, всегда открывающая транзакцию.
- **[Приватный адрес `192.168.3.69`]** → вне домашней сети API недоступен. Митигация: вне объёма; решается отдельно (VPN/публикация).
- **[Учётные данные Firebase Admin]** → сервисный ключ — секрет. Митигация: только через переменные окружения, не в репозитории.
- **[Кэш резолва профиля]** → устаревание при смене привязки. Митигация: короткий TTL; привязка пользователя неизменна.
- **[N+1 при резолве]** → лишний запрос на каждый вызов. Митигация: кэш в памяти процесса.

## Migration Plan

1. Развернуть сервис рядом с базой на `192.168.3.69`.
2. Задать окружение: подключение к `mydb`, учётные данные Firebase Admin.
3. Проверить: запрос без токена → 401; со своим токеном → 200; чужой продукт → 404.
4. Откат: остановить сервис; база и спеки не менялись.

## Open Questions

- Как запускать сервис (systemd, Docker, pm2) — определяется при развёртывании.
- Как клиент попадёт в сеть `192.168.3.69` — отдельное решение.
- Нужен ли TLS для внутреннего трафика — до внешнего доступа.
