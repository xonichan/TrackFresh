# Design

## Context

См. proposal.md — Why. API (`data-api`) слушает порт на `192.168.3.69` и доступен только в домашней сети. Аутентификация — Firebase ID-токен в заголовке `Authorization`. Домена нет, поэтому сертификат самоподписанный. Клиент (`create-trackfresh-app`) собирается через Expo prebuild, то есть нативная конфигурация Android ему доступна.

## Goals / Non-Goals

**Goals:**
- Сделать API доступным извне, сохранив шифрование трафика.
- Не ослабить проверку токена и изоляцию данных.
- Ограничить нагрузку на публичной точке входа.

**Non-Goals:**
- Покупка домена и публично доверенный сертификат.
- VPN вместо публикации.
- Изменения API, схемы БД и логики приложения, кроме адреса и доверия к сертификату.

## Decisions

### 1. Обратный прокси на `192.168.3.69`
**Выбор**: nginx или Caddy на том же сервере, наружу открыт только его порт; API слушает `localhost` и наружу не смотрит.
**Rationale**: сервис не должен быть доступен напрямую; прокси даёт TLS, перенаправление и ограничение частоты в одном месте.
**Альтернатива**: TLS внутри самого API — размазывает ответственность и требует правки кода.

### 2. Собственный удостоверяющий центр и сертификат
**Выбор**: локальный УЦ (openssl), серверный сертификат подписан им; домена в сертификате нет — используется IP в поле SAN.
**Rationale**: домена нет, публично доверенный сертификат выпустить не на что.
**Следствие**: сертификат надо вшивать в клиент (см. решение 4) и менять при ротации вместе со сборкой приложения.

### 3. SAN с IP, а не с именем
**Выбор**: в сертификате поле `subjectAltName = IP:<внешний адрес>`.
**Rationale**: Android проверяет SAN, а не CN; при обращении по IP без SAN соединение не установится даже с доверенным сертификатом.

### 4. Доверие в приложении через конфигурацию сетевой безопасности
**Выбор**: корневой сертификат кладётся в ресурсы приложения, а `network_security_config.xml` разрешает доверять только ему для внешнего адреса.
**Rationale**: React Native на Android использует системное хранилище; самоподписанный сертификат система не примет без явного доверия. Expo prebuild позволяет положить нативный конфиг.
**Отклонено**: отключение проверки сертификата в клиенте — убирает смысл HTTPS.

### 5. Перенаправление HTTP на HTTPS
**Выбор**: отдельный порт отвечает только перенаправлением, данные по нему не идут.
**Rationale**: набранный вручную `http://` адрес не должен молча отдавать токен открытым текстом.

### 6. Ограничение частоты на прокси
**Выбор**: лимит запросов с одного адреса, ответ 429.
**Rationale**: публичная точка входа сканируется автоматически; проверка токена защищает данные, но не от нагрузки.

### 7. Адрес клиента — параметр сборки
**Выбор**: внешний базовый адрес задаётся в конфигурации приложения, а не хардкодится в коде экранов.
**Rationale**: при смене IP или порта правка должна быть в одном месте.

## Risks / Trade-offs

- **[Динамический публичный IP]** → домена нет, адрес зашит как IP; при смене адреса провайдером сертификат (SAN с IP) и приложение перестают работать. Митигация: DDNS-имя даже без покупки домена — тогда меняется только DNS; в текущем решении это не сделано, риск принят сознательно.
- **[Ротация сертификата требует новой сборки]** → вшитый корневой сертификат живёт в приложении. Митигация: выпускать сертификаты с длинным сроком и не менять корневой сертификат при продлении серверного.
- **[Публикация домашнего сервера]** → открытый порт расширяет поверхность атаки: сканирование, нагрузка, попытки подбора. Митигация: только HTTPS, лимит частоты, проверка токена, обновления прокси и API.
- **[Прокси и API на одном узле]** → падение узла убирает доступ. Митигация: отдельный процесс, автозапуск, возможность перезапуска.
- **[Самоподписанный сертификат]** → пользователь не увидит предупреждения браузера, но и подтверждения подлинности нет; доверие держится на вшитом центре. Митигация: принять как известное ограничение.

## Migration Plan

1. Выпустить корневой и серверный сертификаты, проверить их на сервере.
2. Поднять прокси с TLS, перенаправлением и лимитом; убедиться, что API отвечает через прокси.
3. Настроить перенаправление порта на роутере, проверить доступ из мобильной сети.
4. Положить корневой сертификат в приложение и переключить базовый адрес на HTTPS.
5. Откат: остановить прокси и закрыть порт на роутере; API остаётся доступен в локальной сети как раньше.

## Open Questions

- Статический ли публичный IP у провайдера — если динамический, решение придётся пересматривать.
- Нужен ли VPN для административного доступа к серверу.
- Кто обновляет сертификаты и как узнают о скором истечении.
