# Proposal

## Why

API живёт на `192.168.3.69` и доступен только из домашней сети, поэтому приложение бесполезно везде, кроме дома. Нужен доступ извне, не ломая уже принятую модель безопасности: единственный барьер — проверка Firebase-токена на сервере.

## What Changes

- На `192.168.3.69` поднимается обратный прокси, который принимает HTTPS и передаёт запросы локальному API.
- Выпускается собственный удостоверяющий центр и серверный сертификат для него; сертификат самоподписанный, домена нет.
- На роутере открывается порт наружу; HTTP-запросы на прокси не обслуживаются, только HTTPS.
- Прокси ограничивает частоту запросов с одного адреса.
- Приложение доверяет только этому сертификату: корневой сертификат вшивается в сборку, остальные сертификаты сервера не принимаются.
- Базовый адрес API в приложении меняется на внешний HTTPS-адрес.

## Capabilities

### New Capabilities

- `remote-access`: доступ к API из внешней сети — только по HTTPS, с доверием к конкретному сертификату и ограничением частоты запросов.

### Modified Capabilities

_Нет — требования `data-api` не меняются: проверка токена остаётся прежней._

## Impact

- Новая конфигурация на `192.168.3.69`: обратный прокси, самоподписанный УЦ, серверный сертификат, ограничение частоты.
- Настройка роутера: перенаправление внешнего порта на `192.168.3.69`.
- Клиент: корневой сертификат в сборке приложения, внешний базовый адрес, обработка ошибки сертификата.
- **Риск адреса**: домена нет, поэтому адрес в приложении — IP. Если публичный IP у провайдера динамический, адрес перестанет работать при его смене; перевыпуск сертификата и новая сборка приложения тоже потребуются при ротации.
- Вне объёма: push-уведомления, офлайн-режим, изменения схемы и API.
