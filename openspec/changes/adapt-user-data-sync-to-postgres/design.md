# Design

## Context

См. proposal.md — Why. Спецификация `user-data-sync` описывает Firestore, хотя хранилище уже переведено на PostgreSQL (изменение `define-postgres-data-model` заархивировано, миграция `0001_init_data_model.sql` применена к `mydb`). Аутентификация остаётся на Firebase Authentication.

## Goals / Non-Goals

**Goals:**
- Согласовать требования хранения с фактической схемой PostgreSQL.
- Определить, как профиль пользователя связывается с учётной записью Firebase.

**Non-Goals:**
- Способ подключения приложения к базе и передача идентичности в RLS.
- Офлайн-синхронизация.
- Доставка push-уведомлений.

## Decisions

### 1. Идентификатор Firebase хранится отдельным полем, а не как первичный ключ
**Выбор**: `users.firebase_uid text NOT NULL UNIQUE`; `users.id` остаётся суррогатным `uuid`.
**Rationale**: Firebase UID — строка переменной длины (обычно 28 символов) из произвольного алфавита, она не соответствует формату `uuid`. Хранить её в `users.id` типа `uuid` невозможно без преобразования.
**Альтернативы**:
- Хешировать UID в UUID — необратимо, теряется трассируемость к Firebase Console.
- Сменить тип `users.id` на `text` — ломает существующие FK (`products.user_id`, `user_settings.user_id`) и приведение в RLS-политиках.

### 2. Остальная схема не меняется
Хранение продуктов и настроек уже покрыто таблицами `products` и `user_settings` из миграции `0001`; требуется только новое поле в `users`.
**Rationale**: минимальное изменение, без переписывания FK и политик.

### 3. Идентичность в RLS по-прежнему `users.id`
**Выбор**: `app.user_id` содержит `users.id`, а не Firebase UID.
**Rationale**: Политики уже написаны под `uuid`. Поиск профиля по `firebase_uid` выполняется до установки `app.user_id`.
**Следствие**: на каждый запрос нужен резолв «Firebase UID → users.id» (кэшируется в API-слое, который вне объёма).

### 4. Офлайн-доступ выносится из спеки
**Rationale**: Firestore давал persistence «из коробки»; у PostgreSQL такого механизма нет. Оставлять требование — значит держать в спеке невыполнимое поведение. Проектируется отдельным изменением.

## Risks / Trade-offs

- **[Дополнительный резолв UID → id]** → лишний запрос на каждый вызов. Митигация: кэш в API-слое; вне объёма этого изменения.
- **[`NOT NULL` на существующих строках]** → в `mydb` остались тестовые профили, а колонка добавляется как обязательная. Митигация: удалить тестовые строки перед добавлением ограничения (данные не продуктовые).
- **[Поведение без сети не определено]** → после удаления требования офлайн-доступа приложение без сети не имеет контракта. Митигация: зафиксировать в отдельном изменении до релиза.

## Migration Plan

1. Удалить тестовые профили из `users` (остатки проверок), чтобы таблица была пуста.
2. `ALTER TABLE users ADD COLUMN firebase_uid text NOT NULL UNIQUE` — таблица пуста, поэтому обязательность и уникальность применяются сразу, без промежуточного заполнения.
3. Проверить: дубликат отклоняется, поиск по `firebase_uid` возвращает один профиль, RLS по-прежнему ограничивает доступ.
4. Откат: `ALTER TABLE users DROP COLUMN firebase_uid`.

## Open Questions

- Как API получает Firebase-токен и превращает его в `users.id` — определяется вместе с API-слоем.
