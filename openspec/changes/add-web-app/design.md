# Design

## Context

См. proposal.md — Why. Клиент (`mobile/`) — Expo-приложение на React Native: экраны, состояние, клиент API, очередь изменений. Серверная часть (`api/`) уже умеет проверять Firebase-токен и изолировать данные. Раздавать файлы интерфейса он пока не умеет: в `app.ts` только `/health`, `/products`, `/settings`.

Что проверил в проекте: `react-dom` и `react-native-web` не установлены, платформа web не включена. Библиотеки `@react-native-firebase/auth`, `@react-native-ml-kit/text-recognition` и `@react-native-google-signin/google-signin` — нативные, в браузере не работают. `@react-native-async-storage/async-storage` в браузере работает поверх `localStorage`.

## Goals / Non-Goals

**Goals:**
- Полный набор операций с продуктами и настройками в браузере.
- Одна кодовая база с Android-приложением там, где это возможно без натяжек.
- Раздача интерфейса с того же адреса, что и данные.

**Non-Goals:**
- Сканирование упаковки и напоминания в браузере.
- Офлайн-обещания для браузера.
- Отдельный лендинг, доступ из интернета, TLS.

## Decisions

### 1. Expo web и `react-native-web`, а не второе приложение
**Выбор**: включить платформу web в существующем `mobile/`, собирать через `npx expo export --platform web`.
**Rationale**: экраны, состояние и логика уже написаны на React Native; второе приложение с нуля продублировало бы и разошлось бы с первым.
**Цена**: часть модулей придётся разделить по платформам (см. решения 2–3).

### 2. Аутентификация — два варианта одного модуля
**Выбор**: `AuthContext.native.tsx` на `@react-native-firebase/auth`, `AuthContext.web.tsx` на Firebase JS SDK (email/пароль и Google через всплывающее окно). Оба дают один и тот же интерфейс: `ready`, `user`, `signIn`, `signUp`, `signInWithGoogle`, `signOut`, `getToken`.
**Rationale**: нативный SDK в браузере не работает вовсе, а Firebase JS SDK не работает в React Native. Это единственное место, где выбор платформы неизбежен.
**Риск**: два файла вместо одного — расхождение поведения между ними придётся ловить тестами и вручную.

### 3. Сканирование и напоминания отключены на web
**Выбор**: `useLabelScan` и `notifications` получают веб-варианты, которые ничего не делают и явно сообщают «недоступно»; экран добавления не получает `onScan` на web, поэтому кнопки нет.
**Rationale**: ML Kit и планировщик уведомлений — нативные. Обещать в браузере то, что не работает, хуже, чем не показывать вовсе.
**Следствие**: `DataContext` на web не должен тянуть `expo-notifications` в графе импортов — иначе сборка потянет нативный модуль.

### 4. Файлы интерфейса раздаёт сам API
**Выбор**: статика отдаётся из каталога, куда собирается веб-версия; запросы к `/products`, `/settings`, `/health` остаются маршрутами данных.
**Rationale**: один адрес — нет CORS, нет второго сервера, нет отдельного сертификата.
**Ловушка**: возврат главной страницы для клиентских маршрутов не должен перехватывать маршруты данных и их ответы «не найдено». В Express 5 шаблон вида `*` недопустим — нужен именованный вариант, а возврат страницы — только для GET и не для известных путей данных.

### 5. Настройки Firebase — из одного места
**Выбор**: общие ключи проекта (`projectId`, `authDomain`, идентификаторы клиентов) кладутся в `app.json` → `expo.extra`; для Android остаётся `google-services.json`.
**Rationale**: два независимых источника настройки разошлись бы при первой же смене проекта.

### 6. Стили остаются общими
**Выбор**: те же компоненты и `StyleSheet` из существующих экранов, без второго набора стилей и без CSS-фреймворка.
**Rationale**: `react-native-web` превращает `StyleSheet` в CSS; заводить рядом Bootstrap значило бы поддерживать две разметки для одних экранов.
**Отклонение**: в общих рекомендациях проекта фигурировал Bootstrap для веба — здесь он не используется сознательно.

### 7. Возможность, а не платформа
**Выбор**: недоступная в браузере возможность сообщает о себе сама — `useLabelScan` отдаёт `available`, напоминания — `remindersAvailable`; экраны эти флаги читают и не знают, на чём запущены.
**Rationale**: сначала был заведён признак `isWeb`, но тогда каждый экран решал бы сам, что скрывать. Со временем появились бы разные наборы скрытого на разных экранах.
**Следствие**: проверок платформы внутри экранов нет вовсе; `src/lib/platform.ts` не понадобился и был удалён.

## Risks / Trade-offs

- **[Два варианта платформенных модулей]** → аутентификация и напоминания существуют в двух файлах. Митигация: одинаковый интерфейс и тесты на общий слой; расхождение ловится вручную.
- **[Возврат главной страницы может спрятать ошибки API]** → неверный шаблон fallback начнёт отдавать HTML вместо ответа «не найдено». Митигация: сценарии в дельте `data-api` требуют обратного; задача на проверку именно несуществующего продукта.
- **[Тяжёлый бандл]** → Firebase JS SDK заметно увеличивает размер страницы. Митигация: принять; при необходимости грузить вход отдельным куском.
- **[Порог цвета: спека против кода]** → `product-management` называет жёсткие 3 дня, а клиент берёт порог из `warnDays`. Веб-версия повторяет поведение клиента, то есть внутри проекта остаётся расхождение. Митигация: зафиксировано здесь; спека `product-management` требует отдельной правки.
- **[Офлайн в браузере не обещан, но может заработать сам]** → общий `DataProvider` тянет очередь, а `localStorage` доступен. Митигация: считаем это непроверенным, обещаний в спеке нет.
- **[Без TLS веб-версия доступна только в домашней сети]** → тот же предел, что у приложения. Митигация: `expose-api-remotely`.

## Migration Plan

1. Включить платформу web и убедиться, что существующие экраны собираются и открываются.
2. Разделить аутентификацию по платформам; веб-вход через Firebase JS SDK.
3. Отключить на web сканирование и напоминания, не допуская нативные модули в веб-сборку.
4. Научить API раздавать статику и возвращать главную страницу для клиентских маршрутов, не задевая маршруты данных.
5. Проверить полный сценарий в браузере: вход, добавление, правка, удаление, настройки.
6. Откат: убрать раздачу статики из API — Android-приложение продолжает работать как прежде.

## Open Questions

- Нужны ли в браузере напоминания средствами браузера (отдельное изменение).
- Нужен ли отдельный адрес для веб-версии вместо общего с API.
- Требуется ли доводить веб-версию до вида лендинга.
