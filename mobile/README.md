# TrackFresh — мобильное приложение

Android-приложение на React Native (Expo prebuild + dev-client). Данные хранятся в PostgreSQL,
приложение работает через HTTP API (каталог `../api`, контракт — `../docs/api.md`).

## Что нужно подготовить

1. **Android SDK.** Приложение использует нативные модули (Firebase Auth, ML Kit), поэтому
   Expo Go не подходит — нужна dev-сборка: `npx expo run:android` с подключённым устройством
   или эмулятором.
2. **`google-services.json`** из Firebase Console (Android-приложение с package `app.trackfresh`).
   В репозитории лежит только `google-services.json.example`; положите настоящий файл рядом
   рядом с `app.json` — он в `.gitignore`.
3. **Адрес API** — `app.json` → `expo.extra.apiBaseUrl` (по умолчанию `http://192.168.3.69:3000`).
4. **`expo.extra.googleWebClientId`** — Web client ID из Firebase Console, нужен для входа через Google.

## Запуск

```bash
npm install
npx expo prebuild --platform android   # если каталог android отсутствует
npx expo run:android                   # сборка и установка на устройство
```

## Веб-версия

```bash
npm run build:web    # собирает интерфейс в ../api/public — оттуда его раздаёт API
```

Собранные файлы кладутся в `api/public/` (каталог в `.gitignore`); API отдаёт их с того же
адреса, что и данные, поэтому отдельный сервер и CORS не нужны. Открывается по корню адреса API.
При разработке интерфейса удобнее `npx expo start --web`.

Что в браузере работает иначе:

| Возможность | Телефон | Браузер |
|---|---|---|
| Вход | `@react-native-firebase/auth` + Google Sign-In | Firebase JS SDK, `expo.extra.firebaseWeb` |
| Сканирование упаковки | ML Kit, камера | недоступно: кнопки нет, поля заполняются вручную |
| Напоминания | локальное расписание на устройстве | недоступно: экран настроек предупреждает об этом |
| Продукты, настройки, список, фильтр, цвета | + | + |

Для браузера нужны ключи Firebase в `app.json` → `expo.extra.firebaseWeb` (`apiKey`, `authDomain`,
`projectId`, `appId`). Без них страница открывается, но вход не работает и сообщает об этом.

Платформенные различия живут в файлах-двойниках: `AuthContext.native.tsx` и `AuthContext.web.tsx`,
`notifications.*`, `useLabelScan.*`. Metro выбирает нужный по платформе; для проверки типов рядом
лежат `.d.ts` с описанием поверхности. Обычный код общий — новые экраны пишутся один раз.

Пошаговая проверка веб-версии — в `../docs/web-check.md`.

## Структура

| Путь | Назначение |
|---|---|
| `src/api/` | клиент HTTP API и типы ответов |
| `src/state/` | состояние входа (Firebase) и данных (продукты, настройки) |
| `src/screens/` | экраны: вход, список, добавление, детали, правка, настройки |
| `src/components/ProductForm.tsx` | общая форма продукта и её проверки |
| `src/lib/expiry.ts` | статус срока годности и цвета индикации |
| `src/lib/ocr-parse.ts` | разбор названия и даты из текста упаковки |
| `src/lib/notifications.ts` | локальные напоминания |
| `src/lib/useLabelScan.ts` | камера + ML Kit |
| `src/lib/local-store.ts` | локальное хранилище (продукты, настройки, очередь) |
| `src/lib/queue.ts` | очередь изменений, уплотнение, разрешение конфликтов |
| `src/lib/sync.ts` | отправка очереди на сервер |

## Работа без сети

- Продукты и настройки лежат на устройстве (AsyncStorage). При старте сначала показывается
  сохранённое, затем данные подтягиваются с сервера.
- Добавление, изменение и удаление применяются локально сразу и попадают в очередь отправки.
- Очередь уходит на сервер при старте, после каждого изменения и повторяется каждые 30 секунд,
  пока что-то осталось. Пока изменений нет на сервере, в списке висит признак «Нет связи».
- Уплотнение очереди: `create`+`update` → `create` с новыми полями, `create`+`delete` → ничего,
  `update`+`delete` → `delete`, несколько `update` → последний. Промежуточные состояния
  на сервер не уходят.
- Конфликты разрешаются по времени изменения: побеждает более позднее. Время серверной версии
  (`updated_at`) при локальной правке не затирается — иначе сравнивать было бы не с чем.
  Если сервер ушёл вперёд сильнее чем на 5 минут, это скорее расхождение часов — приложение
  показывает «Данные обновлены с сервера».
- Клиент сам создаёт `id` продукта и присылает его в `POST /products`: повторная отправка после
  обрыва связи не создаёт второй продукт.
- Ответы `404` (продукта уже нет) и `409` при создании считаются выполнением: очередь не застревает.

## Ограничения текущего объёма

- Напоминания только локальные; рассылка по расписанию с сервера — отдельное изменение.
- Внешний доступ к API по HTTPS — отдельное изменение (`expose-api-remotely`).
- Синхронизация работает, пока приложение открыто; фоновой работы нет.
- В браузере нет сканирования упаковки и напоминаний, офлайн-работа там не проверялась.
